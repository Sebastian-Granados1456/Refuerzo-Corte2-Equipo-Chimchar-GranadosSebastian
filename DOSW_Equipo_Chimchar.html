Tres problemas reales del MVP de SkyCampus

Problema 1: Una Mision tiene campos obligatorios (drone, origen, destino) y opcionales (prioridad, notas del operador, hora máxima de entrega). Crear un constructor para cada combinación es insostenible y confuso.

Problema 2: Antes de lanzar el drone, el sistema debe validar en orden: (a) ¿el drone tiene batería suficiente? (b) ¿el destino es válido? (c) ¿la carga no supera el peso máximo? Cada validación decide si pasa o rechaza.

Problema 3: El sistema debe asignar el drone óptimo para cada misión. El MVP asigna el de mayor batería. En el futuro podría ser el más cercano, o el más rápido. El algoritmo debe ser intercambiable sin tocar el resto del código.

Tabla de reconocimiento

class MisionBuilder {
    private Drone  drone;
    private String origen, destino;
    private String notas    = "";      // opcional
    private int    prioridad = 3;      // opcional, default medio

    public MisionBuilder drone(Drone d)    { this.drone   = d;  return this; }
    public MisionBuilder origen(String o)  { this.origen  = o;  return this; }
    public MisionBuilder destino(String d) { this.destino = d;  return this; }
    public MisionBuilder notas(String n)   { this.notas   = n;  return this; }
    public Mision        build() {
        if (drone == null || origen == null || destino == null)
            throw new IllegalStateException("drone, origen y destino son obligatorios");
        return new Mision(drone, origen, destino, notas, prioridad);
    }
}

Los nuevos problemas de la v2

Problema 1 (Strategy): El sistema debe asignar el drone óptimo para cada misión. Hoy asigna el de mayor batería. Mañana podría ser el más cercano. La semana siguiente, el de menor uso acumulado. El algoritmo debe ser intercambiable sin tocar GestorMisiones.

// STRATEGY — algoritmos de asignación intercambiables
interface EstrategiaAsignacion {
    Optional<Drone> seleccionar(List<Drone> flota, Mision mision);
}
class AsignacionMayorBateria implements EstrategiaAsignacion {
    public Optional<Drone> seleccionar(List<Drone> flota, Mision m) {
        return flota.stream()
            .filter(Drone::disponible)
            .filter(d -> d.capacidadGramos() >= m.pesoPaqueteGramos())
            .max(Comparator.comparingInt(Drone::bateria));
    }
}
// Nueva estrategia: agregar clase, cero cambios a GestorMisiones (OCP)

// OBSERVER — notificaciones automáticas de cambio de estado
interface ObservadorDrone {
    void onEstadoCambiado(Drone drone, EstadoDrone nuevo);
}
class GestorFlota {
    private final List<ObservadorDrone> obs = new ArrayList<>();
    void suscribir(ObservadorDrone o) { obs.add(o); }
    void cambiarEstado(Drone d, EstadoDrone nuevo) {
        // actualiza el estado...
        obs.forEach(o -> o.onEstadoCambiado(d, nuevo));
    }
}

03 · Patrones de Diseño

Composite · Abstract Factory · Strategy · Observer · cuándo NO usar

Nuevos problemas, nuevos patrones

Problema 1 (Composite): Una "ruta" en Enterprise puede ser simple (punto A a punto B) o compuesta (punto A → estación de carga → punto B). Ambas deben calcularse y ejecutarse de la misma manera desde el GestorMisiones.

Problema 2 (Abstract Factory): Cada sede tiene su propio panel de monitoreo con reportes en formato diferente (ECI usa HTML, UNAL usa PDF, Uniandes usa JSON para su propio dashboard). Abstract Factory crea la familia de reportes coherente por sede.

Cuándo NO usar un patrón

PatrónNo usar cuando...Alternativa
SingletonEstado mutable compartido entre hilos (flota compartida)Inyección de dependencias con scope de sesión
Abstract FactorySolo hay una familia de componentesFactory Method simple
CompositeLa jerarquía nunca tiene más de 2 nivelesLista simple con herencia

    boolean condicionesAptas(String origen, String destino);

    }
    // 100% testeable: solo inyectar mocks en las pruebas
}
